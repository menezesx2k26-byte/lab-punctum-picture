# TDD fix for the Clerk production proof plus a turnkey Codespaces R4 live-QA harness (v1)

This branch does three things: repairs a build-breaking stale import in `scripts/hostinger-clerk-production-proof.mjs`, adds a fail-closed GitHub Codespaces orchestrator that reuses the existing R4 gate scripts (`.devcontainer/devcontainer.json`, `scripts/qa/r4-codespace-gates.mjs` + node-test, `qa:r4`/`qa:r4:local` npm scripts, `CODESPACE-R4-QA.md`), and appends one R4 ledger cycle entry to `execution-state.json`. The fix swaps a removed `setAdminPassword` export for `prepareAdminPassword` and runs the prepared statement; no production auth code changes. The harness never reimplements a gate — it shells out to the real scripts, SKIPs any gate whose secrets are absent, and exits non-zero only when a gate that actually ran failed. The security contract holds: no JWT/issuer/azp/session/revocation check is touched, no test assertion is weakened, no secret value is committed, and no gate is promoted.

Watch for: the devcontainer `secrets` block omits two names that the G17 gate requires — `HOSTINGER_API` and `PUNCTUM_MANAGED_OUTPUT` — so G17 can never RUN via the documented Codespaces setup, and `CODESPACE-R4-QA.md`'s claim that the devcontainer "declares the same names" is therefore inaccurate (confirmed). This is fail-closed (G17 SKIPs, never fake-passes), so it is a functional/documentation gap, not a security break.

**Verdict**: NEEDS_CHANGES

## High-level view

The code defect was a real build failure: `worker/utils/auth.ts` renamed `setAdminPassword` (which executed its write) to `prepareAdminPassword` (which returns an unexecuted `D1PreparedStatement`). The esbuild bundle in the proof still imported the old name, so the bundle failed and three anonymous-admin-denial proof tests broke. The fix imports the new name and calls `.run()` on the returned statement. Worker auth source is untouched and the proof's identity/session assertions are intact.

The orchestrator's SKIP/RUN decision is a pure function (`decideGate`/`missingSecrets`) driven by a per-gate `requiredSecrets` NAME list: a name counts as present only when its env value is a non-blank string. Local no-secret gates always RUN; live gates SKIP when any required name is absent, and `--local-only` forces every live gate to SKIP regardless of env. A gate that RUNs and exits non-zero (or fails to spawn) is recorded FAIL and makes the process exit 1; an all-SKIP run exits 0 by design ("nothing proven, nothing faked"), so a green exit does not imply gates passed.

The API surface is two npm scripts (`qa:r4`, `qa:r4:local`) and evidence written under `outputs/qa-r4-codespace/` (`summary.json` plus per-gate JSON, mode 0600). Secret handling is name-only throughout: evidence records `requiredSecrets` names and captured child output, never values, and a dedicated test asserts a sentinel secret value never appears in stdout/stderr, `summary.json`, or any per-gate file.

The gap is in gate reachability, not safety. G17 (`scripts/hostinger_managed_production.py`) requires `HOSTINGER_API` (the Hostinger harness raises if it is unset) and `PUNCTUM_MANAGED_OUTPUT` (a path it reads), but neither name is in the devcontainer `secrets` block, so Codespaces won't prompt for them and G17 will perpetually SKIP under the documented flow. Because G18/G23 depends on G17's `report.json`, it also can't close without G17 running. The doc lists both names in its instructions yet states the devcontainer declares the same set, which is not true for these two.

The ledger change is an append-only new key (`currentCycleSandboxReverify20261123`); top-level `status`, `decision`, `releasePackageVerdict`, `completionVerdict`, and the prior cycle records are unchanged, and the new block self-declares `gateStateChange: NONE` with historical-only counts and `NO_GO_PRODUCTION`.

## The stale `setAdminPassword` import and why the fix is correct

`worker/utils/auth.ts:340` defines `prepareAdminPassword`, which builds the `INSERT ... ON CONFLICT` upsert and returns a `D1PreparedStatement` without executing it. The previous export, `setAdminPassword`, ran the write itself. The proof bundles the worker via esbuild (`loadAuthHandlers`) and its `stdin.contents` still re-exported `setAdminPassword`, so the bundle failed with "No matching export for import setAdminPassword" and took down the two anonymous-admin-denial proof tests (red: 3/6 fail).

The fix is two lines: the re-export now names `prepareAdminPassword`, and the legacy-fallback setup calls `await (await auth.prepareAdminPassword(password, db, "proof@example.invalid")).run()`. The change lives only in the proof's setup path; the assertions that follow (legacy login returns 200, and the Clerk identity/session checks at `scripts/hostinger-clerk-production-proof.mjs:36-47`: active session, unexpired `expire_at`/`abandon_at`, verified primary email, user-id/session-id binding) are unchanged. `git diff` against the baseline shows no change under `worker/`, so no JWT signature, issuer, audience, azp, session, or revocation logic is affected. Confirmed green locally: `node --test scripts/hostinger-clerk-production-proof.test.mjs` → 6/6.

## The all-SKIP exit path

An all-SKIP run exits 0 (the test `all-skip run exits 0 and never spawns a child` locks it in), so any downstream workflow that treats a zero exit as "R4 gates passed" would be wrong; it must read `summary.totals.ran`/`passed`/`skipped`. `runGate` treats a non-zero exit, a signal, or a spawn error (`ENOENT`) as FAIL, and `main` sets `exitCode = ranFailures > 0 ? 1 : 0`, counting only gates that actually ran.

```
secrets present? ──no──► SKIP (lists missing NAMES)        exit unaffected
      │yes
--local-only & live? ──yes──► SKIP (live gate)             exit unaffected
      │no
     RUN ──► child exit 0 ─► PASS
             child exit≠0 / signal / spawn error ─► FAIL ─► exit 1
```

## G17 reachability gap: devcontainer and doc disagree with the gate

The G17 gate runs `python3 scripts/hostinger_managed_production.py`, and `r4-codespace-gates.mjs` lists its `requiredSecrets` as `HOSTINGER_API`, `SOURCE_ADMIN_EMAIL`, `SOURCE_ADMIN_PASSWORD`, `PUNCTUM_MANAGED_OUTPUT`, `GITHUB_SHA`. Both `HOSTINGER_API` and `PUNCTUM_MANAGED_OUTPUT` are genuine runtime inputs: `scripts/hostinger_managed_qa.py:86-88` reads `HOSTINGER_API` and raises "HOSTINGER_API is unavailable" if unset, and `hostinger_managed_production.py:129` reads `os.environ['PUNCTUM_MANAGED_OUTPUT']` as the export directory. Neither name appears in the devcontainer `secrets` block (which declares 22 names; these two are absent). Because Codespaces only prompts for names it sees in that block, the owner following the documented setup will never be offered these two, and `missingSecrets` will keep G17 at SKIP.

`CODESPACE-R4-QA.md` compounds the mismatch. Section 2 lists both names under "Managed origin (G05 remote, G06-G14, G17)" while also asserting that `.devcontainer/devcontainer.json` "declares the same names so Codespaces prompts for any that are missing." The two statements can't both be true as shipped. The failure mode is safe — G17 fails closed to SKIP and never fake-passes — but the harness advertises a G17 (and, transitively, a G18/G23 that needs G17's `outputs/punctum-managed-production/report.json`) that the documented path can't actually run. Either add the two names to the devcontainer secrets block or correct the doc's claim.

## Secret-value containment

Name-only handling is consistent across the harness. The plan log and per-gate evidence record `requiredSecrets` NAMES plus captured child stdout/stderr (the underlying gate scripts are written not to echo secrets), and `summary.json` records the source SHA (a non-secret CI provenance value) but no secret. The test `secret VALUES never appear in printed output, summary.json, or per-gate evidence` injects a sentinel `sk_live_...` into every secret name, runs `main`, and asserts the value appears in none of the captured output or files. Evidence files are written mode 0600. A scan of the added lines for `sk_live_`/`pk_live_`/`user_`/`sess_`/JWT patterns finds only that sentinel inside the test and documentation placeholders (`sk_live_...`), no real values.

## Test coverage

The orchestrator node-test (11/11) covers the decision matrix end to end: local gates require no secrets, blank/whitespace counts as missing, no-secrets → every live gate SKIP with the exact missing list, `--local-only` skips live gates even with all secrets set, a fully-secret gate RUNs, a simulated failing child → FAIL + exit 1, a spawn error → FAIL, the all-SKIP exit-0 path, secret-value non-leakage, and the external-gate declaration (`G15/G19/G20/G22` are not runnable). The production proof test (6/6) exercises the repaired bundle and the identity-binding assertions.

Not tested: the two real failure modes that would most affect an owner's run can't be unit-tested here and aren't — a real child-process gate against a live origin, and the G17→G18/G23 `report.json` handoff. These are environment-gated by design, but the devcontainer secret-name gap above means the one path an owner is told to follow would silently SKIP G17 rather than surface a configuration error, and nothing in the suite flags the devcontainer/harness name divergence. A small test asserting that every `GATES[].requiredSecrets` name (minus the non-secret `GITHUB_*` provenance) is declared in the devcontainer secrets block would have caught this.
